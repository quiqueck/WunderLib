# Migrating to WunderLib 26.x (Minecraft 26.1)

This guide is for mod developers who depend on **WunderLib** and are updating their
mod from the 1.21.x line to **Minecraft 26.1**. It covers the toolchain changes, the
changes to WunderLib's own public API, and the underlying vanilla/Fabric changes that
surface through WunderLib.

WunderLib `26.0.0` targets Minecraft `26.1`, `26.1.1`, `26.1.2`.

> **Scope note.** Minecraft 26.1 is a large jump. This guide focuses on what a *WunderLib
> consumer* has to change. For the full vanilla change set, see the Fabric 26.1 porting
> guide and the NeoForge/Minecraft-wiki primers.

---

## 1. Toolchain / build script

| Thing | Old (1.21.x) | New (26.1) |
| --- | --- | --- |
| Gradle | 8.x | **9.4.0** (`./gradlew wrapper --gradle-version 9.4.0`) |
| Loom plugin id | `fabric-loom` | **`net.fabricmc.fabric-loom`** |
| Loom version | 1.10.x | **1.15.5** |
| Java | 21 | **25** |
| Fabric Loader | 0.16.x | **0.19.3+** |
| Fabric API | `…+1.21.x` | **`0.155.2+26.1.2`** |
| Mappings | Mojang official | Mojang official (unchanged) |
| Publishing | `com.matthewprenger.cursegradle`<br>`com.modrinth.minotaur` | **`me.modmuss50.mod-publish-plugin`** (`2.1.1`) |

`build.gradle` changes:

```diff
 plugins {
-    id 'fabric-loom' version "${loom_version}"
+    id 'net.fabricmc.fabric-loom' version "${loom_version}"
-    id "com.modrinth.minotaur" version "2.+"
-    id "com.matthewprenger.cursegradle" version "1.4.0"
+    id "me.modmuss50.mod-publish-plugin" version "2.1.1"
 }

 dependencies {
     minecraft "com.mojang:minecraft:${minecraft_version}"
-    mappings loom.officialMojangMappings()
-    modImplementation "net.fabricmc:fabric-loader:${loader_version}"
-    modImplementation "net.fabricmc.fabric-api:fabric-api:${fabric_version}"
+    implementation "net.fabricmc:fabric-loader:${loader_version}"
+    implementation "net.fabricmc.fabric-api:fabric-api:${fabric_version}"
 }
```

- **Remove the `mappings` line.** In 26.1 Minecraft ships in official mappings, so Loom
  no longer performs a remap step.
- **`mod*` dependency configurations are gone.** Loom 1.15 removed `modImplementation`,
  `modCompileOnly`, `modApi`, `modLocalRuntime`. Use the plain `implementation`,
  `compileOnly`, `api`, `localRuntime` — Loom remaps mod jars added to the standard
  configurations. (Make sure any third-party mod dependency is a **26.1** build; old
  1.21.x jars leak intermediary `class_1234` names.)
- **`remapJar` → `jar`, `remapSourcesJar` → `sourcesJar`** in any publishing/task wiring.
- Access widener / class tweaker header: `named` → **`official`**.

### 1.1 Mod Publishing migration (replacing `cursegradle` & `minotaur`)

Instead of writing separate, verbose `curseforge { ... }` and `modrinth { ... }` blocks, configure everything inside a single, unified `publishMods` block:

```groovy
publishMods {
    // Optionally tie dryRun to a project property: ./gradlew publishMods -PdryRun
    dryRun = project.hasProperty("dryRun") ? (project.property("dryRun").toString().toLowerCase() in ["true", "", "1", "yes"]) : false
    
    file = jar.archiveFile
    changelog = file("CHANGES.md").exists() ? file("CHANGES.md").getText('UTF-8') : ""
    type = STABLE // Or BETA, or ALPHA
    modLoaders.add("fabric")

    curseforge {
        projectId = project.curseforge_id
        accessToken = ...
        minecraftVersions.add("26.1.2")
        client = true
        server = true
        displayName = "${project.archives_base_name}-${project.mod_version}"
        requires("fabric-api")
    }

    modrinth {
        projectId = project.modrinth_id 
        accessToken = ...
        minecraftVersions.add("26.1.2")
        displayName = "${project.archives_base_name}-${project.mod_version}"
        requires("fabric-api")
    }
}
```

* **Modrinth ID format**: The new plugin strictly requires the unique 8-character alphanumeric Modrinth ID for `projectId` (e.g. `8O0Adq7w`) and will fail local validation if you provide the human-readable slug (e.g. `wunderlib`). It is recommended to define `modrinth_id` in `gradle.properties`.
* **Avoid project ID in `displayName`**: Since the Modrinth ID is a random 8-character string, ensure your `displayName` is constructed using `project.archives_base_name` instead of `projectId` so the release name on CurseForge and Modrinth remains human-readable.
* **Task rename:** Older tasks like `curseforge` and `publishModrinth` are replaced by `publishMods` (or `publishCurseforge`/`publishModrinth` under the new plugin).

### Gradle 9 gotchas

- `sourceCompatibility = …` / `targetCompatibility = …` at the top level throw
  *"unknown property"* — set them on the `java` extension: `java.sourceCompatibility = JavaVersion.VERSION_25`.
- `archivesBaseName = …` throws — use `base.archivesName = …`; reads become `project.base.archivesName`.
- Space assignment syntax (e.g., `url "..."` in the `repositories` block or `failOnError true` inside `javadoc`) throws or warns — use assignment: `url = "..."` and `failOnError = true`.
- The `archives` configuration has been deprecated for declaring artifacts in the `artifacts { ... }` block. Avoid registering task outputs (like `sourcesJar` or `javadocJar`) using `archives sourcesJar`. Instead, declare them directly as dependencies of the `assemble` task:
  ```groovy
  tasks.assemble.dependsOn(sourcesJar, javadocJar)
  ```

### `fabric.mod.json`

```json
"depends": {
    "fabricloader": ">=0.19.0",
    "fabric-api": ">=0.155.0",
    "minecraft": ["26.1", "26.1.1", "26.1.2"],
    "java": ">=25",
    "wunderlib": "26.0.x"
}
```

## 2. Vanilla renames that surface through WunderLib APIs

These vanilla types changed name/package. If you pass them to (or receive them from)
WunderLib methods, update your imports:

| Old | New |
| --- | --- |
| `net.minecraft.resources.ResourceLocation` | **`net.minecraft.resources.Identifier`** (same API) |
| `net.minecraft.Util` | **`net.minecraft.util.Util`** (same API) |
| `net.minecraft.client.gui.GuiGraphics` | **`net.minecraft.client.gui.GuiGraphicsExtractor`** |

A project-wide find/replace of the token `ResourceLocation` → `Identifier` is safe (it is a
pure rename; `Identifier` keeps `fromNamespaceAndPath`, `parse`, `withDefaultNamespace`,
`tryParse`, `getPath`, `getNamespace`, `withPath`, `CODEC`, `STREAM_CODEC`, …).

## 3. WunderLib UI / rendering API changes (the big one)

26.1 rewrote GUI rendering into an **extract-render-state** pipeline. WunderLib's UI layer
was ported accordingly, and this is the change most likely to touch your code.

### 3.1 `GuiGraphics` → `GuiGraphicsExtractor`

Everywhere WunderLib handed you a `GuiGraphics` (custom renderers, `RenderHelper`,
`ComponentRenderer`, `LayoutComponent` render hooks) you now receive a
**`GuiGraphicsExtractor`**. The common draw calls are the same (`fill`, `blit`,
`blitSprite`, `enableScissor`, `pose()` → `Matrix3x2fStack`), but some were renamed:

| Old (`GuiGraphics`) | New (`GuiGraphicsExtractor`) |
| --- | --- |
| `drawString(font, text, x, y, color)` | `text(font, text, x, y, color, dropShadow)` (returns `void`) |
| `renderItem(...)` | `item(...)` |
| `renderFakeItem(...)` | `fakeItem(...)` |
| `renderItemDecorations(...)` | `itemDecorations(...)` |

### 3.2 Render methods → extract methods

If you subclass a WunderLib component/screen and override a render method, rename it:

| Old override | New override |
| --- | --- |
| `Renderable.render(GuiGraphics, …)` | `extractRenderState(GuiGraphicsExtractor, …)` |
| `Screen.render(GuiGraphics, …)` | `extractRenderState(GuiGraphicsExtractor, …)` |
| `AbstractWidget.render(GuiGraphics, …)` | `extractRenderState(GuiGraphicsExtractor, …)` |

### 3.3 `LayoutScreen` subclasses

If you extend WunderLib's `LayoutScreen` (or `LayoutScreenWithIcon` / `ConfigScreen`):

```diff
-public void renderBackgroundLayer(GuiGraphics guiGraphics, int mouseX, int mouseY, float delta) { … }
+public void renderBackgroundLayer(GuiGraphicsExtractor guiGraphics, int mouseX, int mouseY, float delta) { … }
```

`renderBackgroundLayer` now runs during the **extract** phase.

### 3.4 Input events are records now

`GuiEventListener` / `ContainerEventHandler` / `AbstractWidget` input methods take event
records instead of loose primitives. WunderLib components expose the new signatures:

| Old | New |
| --- | --- |
| `mouseClicked(double, double, int)` | `mouseClicked(MouseButtonEvent, boolean doubleClick)` |
| `mouseReleased(double, double, int)` | `mouseReleased(MouseButtonEvent)` |
| `mouseDragged(double, double, int, double, double)` | `mouseDragged(MouseButtonEvent, double, double)` |
| `keyPressed/keyReleased(int, int, int)` | `keyPressed/keyReleased(KeyEvent)` |
| `charTyped(char, int)` | `charTyped(CharacterEvent)` |

The event types live in `net.minecraft.client.input`. WunderLib's containers preserve the
coordinate offsetting internally, so if you override these on a WunderLib component just
match the new signature.

### 3.5 `Input.setFilter` behaviour

`net.minecraft.client.gui.components.EditBox#setFilter` was removed in 26.1.
`de.ambertation.wunderlib.ui.layout.components.Input#setFilter(Predicate<String>)` is
**unchanged for you** — it still rejects invalid input. WunderLib now enforces it
internally via a `setResponder` revert-on-reject wrapper, so no change is required in your
code. (`setFormatter` is likewise unchanged; it maps onto the new `EditBox#addFormatter`.)

## 4. Networking API changes

If you use WunderLib's networking (`PacketHandler` / `ClientBoundPacketHandler` /
`ServerBoundPacketHandler`) directly, note the underlying Fabric API renames:

| Old | New |
| --- | --- |
| `PayloadTypeRegistry.playS2C()` | `PayloadTypeRegistry.clientboundPlay()` |
| `PayloadTypeRegistry.playC2S()` | `PayloadTypeRegistry.serverboundPlay()` |
| `context.player().getServer()` (server ctx) | `context.server()` |

WunderLib's own network entry points keep their signatures; this only matters if you call
the Fabric registry yourself.

## 5. Runtime pitfalls (not caught by the compiler)

These compile fine but fail at runtime in 26.1 — worth checking in your own mod:

- **Never build an `ItemStack` (or read item data components) at class-load / `static`
  initialiser time.** In 26.1 item data components are bound *after* early mod init, so a
  `static final ItemStack X = new ItemStack(…)` throws `NullPointerException: Components
  not bound yet`. Make such fields lazy (compute on first use) or store the `Item`/`Block`
  and materialise the stack at runtime. The same applies to anything running during the
  datapack reload (e.g. `RecipeManager.prepare`) — components are bound only after the
  reload completes.
- **Mixin targets** that were renamed/removed only fail at *apply* time
  (`InvalidInjectionException: could not find any targets`). Re-check your injection
  targets against the 26.1 jar.

## 6. Version bump

WunderLib moved to a **`26.x`** scheme (major tracks the Minecraft major; the minor is
**independent** of the Minecraft minor). The first 26.1-compatible release is `26.0.0`.
Update your dependency accordingly and bump your own mod version.
